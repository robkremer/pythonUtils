util.terminal module¶

Terminals for an application’s command line, and the routing of its output to them:

  • TerminalWidget: a Tk text widget that behaves like a terminal (a prompt, typed commands, history).

  • PlainTextTerminal: the same interface on the real console (a REPL).

  • TerminalRegistry and installGlobalIORouting(): send stdout, stderr, logging and input() to the terminal of whichever window is active.

util.terminal.writeToRealConsole(text: str, style: str | None = None) → None¶

Last-resort output path: write directly to the real console, bypassing routing entirely. Used when TerminalRegistry.resolveTerminal() can’t find ANY terminal to route to, so output is never silently dropped — just less conveniently placed than it would be in a TerminalWidget.

Deliberately targets sys.__stdout__/__stderr__ (the interpreter’s original streams, unaffected by installGlobalIORouting()’s reassignment of sys.stdout/sys.stderr) rather than the current sys.stdout/sys.stderr, which would just loop back into routing and hit this same fallback again.

Parameters:

  • text (str) – The text to write (a newline is appended).

  • style (Optional[str]) – “stderr” routes to sys.__stderr__; anything else (including None) routes to sys.__stdout__.

_resolveActiveWindowTerminal() → TerminalWidget | None¶

Fallback for resolveTerminal(): find the terminal for whichever registered window is currently frontmost, per the window manager’s stacking order — independent of Tk’s logical keyboard focus.

This covers cases _focusedMainThreadTarget can’t: a click that never moves Tk focus (e.g. SNCanvas’s right-click popup menu), or an exception raised before the user has interacted with the window at all (e.g. during initial model population). ‘wm stackorder’ reports windows lowest-to-highest, so the LAST element is topmost.

Confirmed empirically (headless Tk) that ‘wm stackorder’ must be queried THROUGH THE APPLICATION ROOT (_root()) to get the full sibling list — querying it via one of the child Toplevels themselves returns only that single window, not its siblings, presumably because stacking-group membership is keyed off the group leader (the hidden root here), not off each Toplevel’s Python-level .master.

inputAsync(prompt: str = '', onResult: Callable[[str], None] | None = None, onError: Callable[[BaseException], None] | None = None) → None¶

input(), but safe to call from the main/GUI thread — e.g. a menu command or button handler. Returns immediately; spawns a short-lived worker thread bound to this terminal that calls self.input(prompt), then marshals the result (or any exception) back onto the main thread via onResult/onError.

Calling input() directly and blocking for its return value is never safe from the main thread, no matter how you get there (a plain thread spawn included) — blocking the GUI callback on the worker thread’s result would freeze the event loop exactly as calling input() directly does. The fix is this callback/continuation style: kick off the request, return, and let onResult pick up the answer once it actually arrives.

Parameters:

  • prompt (str) – The prompt text to display (uses the “query” style).

  • onResult (Optional[Callable[[str], None]]) – Called on the main thread with the line the user typed.

  • onError (Optional[Callable[[BaseException], None]]) – Called on the main thread with any exception input() raised (e.g. EOFError on Ctrl+D). If omitted, the exception is logged and otherwise swallowed.

Return type:

None
