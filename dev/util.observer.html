util.observer module¶

An “extended” implementation of the observer/subject design pattern. Instead to the traditional subject calling notify() for every change (which may result in a lot of unnecessary updates happening), we use the “with” clause to more elegantly manage updates:

Within the the Subject’s code…¶
with Subject.ChangeMgr(self) as changeMgr:
  try:
    # make a change
    ...
    changeMgr.registerTopics(("topic1", (value [,...])), ("topic2", (value [,...])))
  except:
    changeMgr.cancel()

In the event the changes are nested (ie: the “<make a change>” section calls other methods with updates), this results in saving up all the notifies until the outer update completes. The registerTopics() method assures that the topics are passed in the eventual notify() method. The cancel() method will suppress the final notify() if all nested updates also resulted in a cancel().

There are two ways you can get event notifications from a Subject object. The first is an Observer object must registers with the Subject as an Observer which obligates the Observer to provide an update() method:

Within the the Observer’s code…¶
  subject.attach(self, "topic1", "topic2")

...

def update(self, subject: Subject, *topics:Tuple[str, Tuple[Any, ...]]) -> None:
  topic:str
  params:tuple[Any, ...]
  for topic, params in topics:
    if topic == "topic1":
      # deal with topic1 and it's params
      ...
    elif topic == "topic2":
      ...

The second way to get a notification is through a callback:

No need for an Observer class…¶
subject.attachCallback(lambda topic, args: print(f'{topic}: {args}), \
                       "topic1", 
                       "topic2")

In this case, the lambda function will be invoked whenever the topic event happens. It could also have been an independent function or a method call.

There is an alternate version of notify(), notifyLater() that works similarly, but deferred until the current call stack unwinds (e.g. until a constructor finishes) instead of firing observers synchronously, mid-construction. Use this anywhere notify() would otherwise let an Observer inspect a not-yet-fully-built object.

Updates (The arguments to Subject.notify() and Observer.update() are expected to be tuples with the first element being a “topic” of str type and the second element being a tuple “arguments” to the topic.

util.observer.enabled: bool = True¶

Use the enabled flag if you must disable all notifications, for example, during initialization or reading in new data from a file. Don’t forget to restore it to True.

util.observer.alwaysLater: bool = False¶

Set this to True for force (application wide) ALL calls to notify to behave as calls to notifyLater.

But if this method is called “later” (usually on the tk event loop), the observers and callbacks should be those AT THE TIME OF THE ORIGINAL NOTIFICATION, not at the time the notification actually eventually happens.

scheduler: Callable[[...], None] | None = None¶
notifyLater(*topics: tuple[str, tuple[Any, ...]]) → None¶

Like notify(), but deferred until the current call stack unwinds (e.g. until a constructor finishes) instead of firing observers synchronously, mid-construction. Use this anywhere notify() would otherwise let an Observer inspect a not-yet-fully-built object.

Tries, in order: an app-supplied scheduler (self.scheduler / Subject.scheduler); tkinter’s default root’s after_idle(), if tkinter is already imported and has a live root; an asyncio event loop’s call_soon()/call_soon_threadsafe(), if one is running; and finally a threading.Timer(0, …) as a last resort.

self._observers/self._callbacks are snapshotted right here, before any of those schedulers run – not read again when the deferred call actually fires – since by then they may have changed (an Observer attached/detached in the meantime, say), and the whole point of deferring is to still deliver the notification this call was actually asked to send. None of the four scheduling mechanisms below reliably accepts extra keyword arguments to forward to the deferred call (Tk’s after_idle() and asyncio’s call_soon()/call_soon_threadsafe() only take *args at all; threading.Timer does take a kwargs= param, but there’s no reason to special-case it), so the snapshot is captured as plain local variables and closed over by a single, argument-less _fireNow(), which every scheduler is just asked to call once, later, with nothing further to pass through.
