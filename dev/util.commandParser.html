util.commandParser module¶

This module defines the following command hierarchy:

Parsable abstract (requires commandName, defineParse())

  • commandName defines the commandName of the command

  • Parsable.topParser the root parser

  • Parsable.immediateSuper the parent SubParsable

  • Parsable.parser the actual argParse.ArgumentParser.

  • _makeParser() responsible for defining the argparse definition. In this case, calls addCommand() on the topParser to make any intermediate subcommands as defined by spliting the commandName.

    SubParsable Non-terminal parser holding subparsers.

    • SubParsable.immediateSuper

    • SubParsable._makeParser() (override) calls addCommaand() on immediateSuper

    • SubParsable.addCommand()

May be a simple commandName like “delete”, in which case the command will be added to this node in the command tree; or it may be a multi-word command path like “modify node commandName”, in which case the any intermediate nodes in the command tree will be created (if they don’t already exist) and the command will be added at the last commandName in the the path.

  • command (Parsable) – A Parsable object to add to the command tree in the position as described above.

  • kwargs – keyword arguments to be passed to the new command’s parser’s constructor (an ArgumentParser)

Add a command to this container and create and return a sub parser for that command. The idea being that commands that change state are Command commands and interact with the DoList while commands that are strictly informational are MutatingCommandGenerator (:> Command ) don’t interact with the DoList .

Note

The commandName parameter may contain spaces indicating a chain of commands, thus you might have command names “modify node” which will create a subparser “modify” with command “node” to execute the command’s code. If later you add command “modify relation”, the “relation” command will be added to “modify“‘s list of commands. Thus you have commands:

> modify node …

> modify relation …

> modify <<Raises a SyntaxError>>

class util.commandParser.CommandContext(parser: TopCommandParser | None = None)¶

Bases: object

A container of commands: each public method is a command, callable from code and parsable from a command line (its name’s words, eg: new_node is “new node”; its parameters, the arguments and options). A method with a matching nested Command class (move() and _Move) is done through the undo list, so it can be undone. Arguments are converted by the context’s decoders, and missing ones filled in from its defaults.

util.commandParser.fixKwargs(fun: Callable, args: list[Any], kwargs: dict[str, Any], defaults: dict[str, Any], decoders: dict[str, Callable[[str], Any]]) → tuple[list[Any], dict[str, Any]]¶

Given a function and a kwargs dict where the kwargs may be from a argParse Namespace (containing extra elements), return a kwargs dict that’s legal for the given function. But also:

  • fill in any defaults for param names that match defaults keys have None values.

  • decode any str param values for types in the fun signature that have str values in kwargs.

  • decode each element of a list-of-str param value (eg: from an argparse nargs) with the decoder for the element type of a list[...] in the annotation (or failing that, for the annotation itself) – unless that allows str (eg: list[str|GraphObject]: the function looks them up).

  • decoders that don’t take **kwargs run first; those that do are then called with the (already decoded) other params as kwargs.

  • a value that won’t decode stays a str if the annotation (or the list’s element type) allows str; otherwise a ValueError naming the param (as --name if it’s an option) is raised, chained from the decoder’s exception.
