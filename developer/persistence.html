Persistence¶

util.persistence saves objects to files and reads them back, with their references to one another intact – including references from one file to another. It’s in two layers:

util.persistence.serialize

Writing and reading objects: any structure of ints, floats, strings, lists, tuples, sets, dicts and Serializable objects, in one of several formats.

util.persistence.pRef

Databases of objects: a file is a PRDb of PRObjects, each with an id, which refer to each other – and to objects in other files – with PReferences.

Serialization¶

A SerializationStrategy writes and reads one format. There are five, each in a module of its own:

name

module

extension

XML3

serializeXML3 (the default)

.xml

XML2

serializeXML2

.xml

XML

serializeXML (the original)

.xml

JSON

serializeJSON

.json

plist

serializePlist

.plist

The class methods are the usual way in:

SerializationStrategy.writex(url, obj)          # in DEFAULT_STRATEGY's format
obj = SerializationStrategy.readx(url)          # whichever format it's in

Reading tries the strategies in turn: those surest, from the first few bytes of the file, that they wrote it (see sniff()), then the ones for its extension, then the preferred ones – so files in any of the formats can be read. XML2 and XML3 write simple values and references as XML attributes, rather than elements of their own, which makes their files around 40% smaller than XML’s.

Documents¶

Written to a file (writex(), write()), an object is a document: a head, then the object (since version 2.0 of the framework, serialize.VERSION). The head is a table of plain values – strings, numbers, booleans, and lists or tables of those; no nulls, objects or references – so any format can hold it and anything can read it. It holds:

  • format, formatVersion: the strategy that wrote it, and its version;

  • serializationVersion: the framework’s version;

  • application, applicationVersion: the program that wrote it (SerializationStrategy.appName, appVersion: set them at start-up);

  • type: the object’s class; saved: when (ISO 8601);

  • the object’s parameters and properties marked inHead (see ParamInfo, PropertyInfo) – eg: a PRDb’s url and superDBs – which aren’t written with it, and are read from the head;

  • what the object adds (its serializationHeader()): eg, a PRDb’s objects (how many) and previousURL; an application’s schema and schemaVersion (the version of its own structures, for migrations).

The head comes first, so it can be read without the rest (readHeadx()): XML3 stops reading at the end of it:

<document>
  <head>
    <property key="format" value="XML3" />
    <property key="type" value="sn.model.model.Model" />
    <property key="objects" type="int" value="122" />
    <property key="superDBs" type="list"> <item value="sn:/sn" /> ... </property>
    ...
  </head>
  <object type="sn.model.model.Model" id="1"> ... </object>
</document>

Other strategies write the two as a table of two entries (head, then object) unless they do better (_tostringDocument()). Documents written before 2.0 (a header and a root) are still read.

An object referred to more than once is written once; later references to it are written by its id, so that after reading, a is b is still true if it was before.

Making a class serializable¶

A class is serializable if it inherits from Serializable and says how to rebuild an instance, in getInstantiationInfo(). That returns an InstantiationInfo made of:

  • constructor arguments – conArgs and conKWArgs: what to pass to the class to make the object;

  • post-construction setters – postconSetters: properties set once it’s made (other objects in the file may not exist yet);

  • final setters – finalSetters: run once the whole file has been read, when every object it refers to exists.

Each item is a ParamInfo or PropertyInfo: a name, a type, and (optionally) a getter and setter, so a class can save its state in whatever form suits it, not just as its attributes. A subclass usually starts from its parent’s InstantiationInfo and adds to it.

Databases of objects¶

A PRDb is a dict-like container of PRObjects, kept in a file (named by a URL). Each object registers itself with its database when it’s made, which gives it an integer id; it may also have a name. Look objects up by either: db[12] or db["fred"].

  • PRDb.getDB(url) returns the database at url: the one in memory if it’s open already, or else read from the file. Open databases are kept in PRDb.AllDBs, so every reference to a file finds the same database.

  • db.save() writes it, in DEFAULT_STRATEGY’s format unless told otherwise. A database is Dirtyable: it knows whether it’s changed since it was last saved. A database can be write-locked.

  • A database is a Subject: it announces objects added ("new") and removed ("del"), so views of it can keep up (see Observers and Changes).

References¶

A PReference refers to an object (or a whole database) without needing it to be loaded: it’s resolved – the file read if need be – when it’s called. Its text forms are:

file:///a/b/pets.snm#12

object 12 in that file

file:///a/b/pets.snm#fred

the object named fred in it

#12, #fred, fred

relative: in the current database

file:///a/b/pets.snm

the whole database

$pets

an open database, by its name

Copied and moved files¶

References between files are written relative to the file being written when the target is close by – in the same folder, below it, or at most PRDb.MAX_UP (2) folders up – so a folder of files can be moved or copied as a block. Further afield, they’re absolute.

Each file’s head records the URL it was saved to (and the one before that). PRDb.readFile() notices when a file is read from somewhere else (it’s been copied or moved), takes it to be where it now is – never confusing it with the original, which may be open too – and reports it. A relative reference that isn’t found next to a copied file is looked for where the original was.
